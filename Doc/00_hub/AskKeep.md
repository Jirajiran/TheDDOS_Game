# เอกสารข้อกำหนดสถาปัตยกรรมระบบพัฒนาเกมและการออกแบบเว็บเกมโฮสต์ (System Architecture & Specification)

เอกสารฉบับนี้จัดทำขึ้นเพื่อสรุปและกำหนดมาตรฐานโครงสร้างสถาปัตยกรรมระบบ (System Architecture) สำหรับระบบพัฒนาเกมและเว็บเกมโฮสติ้ง โดยทำการขจัดข้อมูลบันทึกการแก้ไขรายวัน (Dev Logs) ตัวเลขรุ่นเก่าที่ยกเลิกไปแล้ว และข้อความอภิปรายที่ไม่จำเป็นออกทั้งหมด เพื่อให้ระบบปัญญาประดิษฐ์ (AI Agents) และทีมนักพัฒนาสามารถใช้อ้างอิงโครงสร้างข้อมูล กฎเกณฑ์ และสเตทการทำงานได้อย่างแม่นยำและประหยัดจำนวนโทเค็น (Tokens) ในการประมวลผล

## 1. ภาพรวมระบบและการประมวลผลคำสั่ง (System Architecture & Unified Pipeline)

ระบบถูกออกแบบภายใต้หลักการแยกชั้นหน้าที่ (Decoupled Domain Architecture) เพื่อรองรับการทำงานบนเว็บบราวเซอร์โดยไม่ต้องพึ่งพาเซิร์ฟเวอร์แบ็กเอนด์ในการประมวลผลรอบตรรกะเกม (Static Portfolio Architecture) 

```
[ Input Sources: Player Mouse/Keyboard OR AI Stage Machine ]
                         │
                         ▼
           [ Unified Input Pipeline ]
                         │
                         ▼
        [ Simulation Engine & State Mutators ]
     (Collision / Inventory / Health / Combat / Path)
                         │
                         ▼
             [ Render Engine & App State ]
```

การประมวลผลคำสั่งกระทำผ่านท่อส่งคำสั่งเดียว (Unified Input Pipeline) โดยทั้งผู้เล่น (Player) และยูนิตปัญญาประดิษฐ์ (AI Bot) จะต้องส่งโครงสร้างคำสั่ง (Action Set) เช่น การเคลื่อนที่ (MOVE), การเล็ง (AIM), การยิง (FIRE), การรีโหลด (RELOAD), หรือการวางสิ่งก่อสร้าง (PLACE) เข้าสู่ท่อประมวลผลเดียวกัน ทำให้ยูนิต AI ทำงานอยู่ภายใต้กฎฟิสิกส์ ข้อจำกัดอาวุธ และระบบอินเวนทอรีเดียวกับผู้เล่นโดยสมบูรณ์ โดยไม่มีการข้ามกฎหรือใช้สิทธิ์พิเศษในเชิงระบบ simulation

## 2. สถาปัตยกรรมพิกัดและตารางโลก (Grid & Coordinate System — Set A Standard)

โครงสร้างพื้นที่ของโลกภายในเกมยึดถือมาตรฐานพิกัดชุด Set A เป็นเกณฑ์ความจริงหลัก (Single Source of Truth) โดยยกเลิกการใช้งานระบบพิกัดและขนาดเดิม (800, 400, 200, 100) ทั้งหมด โลกในเกมสร้างขึ้นจากแผ่นพื้นแมพขนาดใหญ่เรียงต่อกันเป็นตาราง $N \times N$ และแบ่งสเกลการประมวลผลออกเป็น 4 ชั้นย่อยดังนี้

โครงสร้างตารางพิกัดแบบลำดับชั้นแบ่งตามขนาดพื้นที่ประกอบด้วย:

| ระดับชั้น (Layer) | ขนาดพิกัด (Pixels) | จำนวนช่องต่อ Path | หน้าที่หลักและกลไกการประมวลผล |
| :--- | :--- | :--- | :--- |
| **Path (L0)** | $1024 \times 1024$ | 1 แผ่นหลัก | หน่วยพื้นที่แมพใหญ่สุด เรียงต่อกันเป็นตาราง $N \times N$ เริ่มวางจากมุมซ้ายบนของจอภาพ |
| **L1 Cell** | $512 \times 512$ | 4 ช่อง | จุดเชื่อมต่อหลักระหว่าง Path (Pivot Points) และใช้คำนวณเส้นทางระดับหยาบของ AI |
| **L2 Cell** | $256 \times 256$ | 16 ช่อง | ทางเดินเชื่อมต่อระดับกลาง ใช้ตัดสินใจหักทิศทางเมื่อยูนิตเคลื่อนที่ข้ามโซน |
| **L3 Cell** | $64 \times 64$ | 256 ช่อง | พิกัดย่อยสุด พอดีกับขนาดยูนิต 1 ตัว และเป็นกริด snap สำหรับวางสิ่งก่อสร้าง (PlaceHold) |

### กลไกโซนคำนวณฐาน (BaseChunk Rules)
สิ่งก่อสร้างฐานหลัก (Base Block V1) มีขนาด $3 \times 3$ ช่องของ L3 (คิดเป็นขนาดรวม $192 \times 192$ พิกเซล) เมื่อมีการสร้างฐาน ระบบจะทำการเปิดใช้งานโซนคำนวณเฉพาะกิจเรียกว่า BaseChunk ทับลงบนพื้นที่ Path 

*   **คุณลักษณะของ BaseChunk**: ซ้อนทับอยู่บนพิกัด Path ไม่ใช่แผ่นโหลดแยก และสามารถทับรอยต่อระหว่างหลาย Path ได้
*   **การปรับเปลี่ยนจุดเดิน**: ในพื้นที่ที่ BaseChunk ซ้อนทับ จุดเชื่อมต่อ L1 (จุดแดง) ของ Path เดิมจะถูกปิดการใช้งาน และเปลี่ยนไปใช้ระบบจุดเดินเฉพาะของ BaseChunk เพื่อให้การกระจายการเคลื่อนที่รอบฐานมีรัศมีเท่ากันทุกทิศทาง
*   **การป้องกันจุดเกิด (Anti-Spawn Buffer)**: ระบบจะห้ามไม่ให้ยูนิตศัตรูกำเนิด (Spawn) ภายในรัศมีของ BaseChunk
*   **สภาวะเมื่อฐานถูกทำลาย**: เมื่อฐานพังทลาย BaseChunk จะถูกปิดใช้งาน และคืนค่าจุดเดิน L1 ของ Path กลับคืนสู่สภาวะปกติ

## 3. สถาปัตยกรรมยูนิตและระบบปฏิสัมพันธ์ (Unit Architecture & Systems)

ยูนิตทุกประเภทภายในเกม (Player, Enemy, Ally) ถูกสร้างขึ้นจากคลาสโครงสร้างเดียวกันคือ `ClassUnit` โดยมีความแตกต่างกันเพียงรหัสประเภท (`typeId`), ทีมสังกัด (Team Faction) และช่องทางการส่งคำสั่งเข้าสู่ Unified Input Pipeline

### ระบบอินเวนทอรีและการจัดการช่องเก็บของ (Inventory Engine)
ยูนิตแต่ละตัวมีช่องเก็บของเริ่มต้น 6 ช่อง และสามารถขยายได้สูงสุด 10 ช่องเมื่อสวมใส่กระเป๋าเป้

*   **กระเป๋าและการอัปเกรด**: เมื่อติดตั้งกระเป๋าเป้แล้วจะไม่สามารถถอดออกได้เพื่อป้องกันไอเทมตก กระเป๋าใบเล็กเดิมจะถูกดรอปลงพื้นเมื่อมีการอัปเกรดเป็นกระเป๋าใบใหญ่ขึ้น ไอเทมกระเป๋าที่ตกบนพื้นจะหมดอายุและถูกลบออกจากระบบขยะภายใน 3 นาที
*   **แถบเลือกใช้งาน (Hotbar)**: สามารถเปิดใช้งานไอเทมได้ทีละ 1 ช่อง (Active Slot) ควบคุมผ่านปุ่มตัวเลขหรือสกอร์ลเมาส์
*   **การจำกัดการซ้อนทับ (Stack Limit)**: ไอเทมแต่ละชนิดกำหนดจำนวนซ้อนทับสูงสุดในไฟล์ข้อมูลเทมเพลต เช่น อาวุธซ้อนทับได้ 1 ชิ้น, ไอเทมวาง PlaceHold ซ้อนทับได้สูงสุด 64 ชิ้น/ช่อง, ยาและระเบิดซ้อนทับได้ 6 ชิ้น/ช่อง
*   **กลไกเมื่อยูนิตเสียชีวิต**: เมื่อยูนิต HP เหลือ 0 ข้อมูลอินเวนทอรีจะไม่ค้างบนตัวยูนิต แต่จะถูกกระจายออกมาเป็นกองไอเทมบนพื้นสูงสุด 6 กอง (ไม่แตก stack ย่อย) และระบบจะนำตัวละครกลับเข้าสู่ Unit Pool เพื่อซ่อนและรอรีเซ็ตนำกลับมาใช้ใหม่

### ระบบการชนและการเคลื่อนที่ (Physics & Collision)
ยูนิตเคลื่อนที่ได้ 360 องศาโดยไม่ล็อกแกนทิศทาง พร้อมระบบคำนวณการชนและการดันกันตามน้ำหนักไอเทม

*   **Unit vs Unit Collision**: เมื่อยูนิตชนกันจะเกิดแรงดัน (Push Force) คำนวณจากผลรวมน้ำหนักไอเทมในอินเวนทอรีของยูนิตแต่ละตัว
*   **Unit vs Environment**: การชนกับสิ่งก่อสร้างและกำแพงใช้กฎฟิสิกส์เดียวกันทั้งผู้เล่นและ AI
*   **การปฏิสัมพันธ์กับสิ่งแวดล้อม (Interaction)**: ประตูใช้การกด Interact ร่วมกับรัศมีวงกลมและการตรวจจับ Raycast เพื่อป้องกันการเปิดประตูทะลุกำแพง การเก็บไอเทมบนพื้นใช้วิธีเดินทับตำแหน่งไอเทม

## 4. สถาปัตยกรรมระบบต่อสู้และอาวุธ (Combat Engine & Damage Matrix)

ระบบอาวุธ (`ClassBaseGun`) เชื่อมต่อกับยูนิตผ่านโครงสร้างคุณลักษณะร่วม ได้แก่ ค่าเกราะป้องกัน (Armor Slot), ความเร็วในการรีโหลด (Reload Speed $0–1$), และการส่ง Action ยิง/หยุดยิง

### โหมดการโจมตี (Attack Modes)
การสร้างความเสียหายแบ่งออกเป็น 2 รูปแบบหลักตามลักษณะของอาวุธ:

1.  **โหมด Projectile ตามเส้นทาง Raycast (Hybrid Projectile)**:
    ใช้เป็นโหมดหลักสำหรับปืนและจรวด เมื่อกดยิง ระบบจะคำนวณเส้นทาง Raycast เพื่อหาทิศทางและระยะทางสูงสุด จากนั้นจะทำจำลอง (Simulation) ตัวกระสุนให้วิ่งไปตามเส้นทางด้วยค่าสเกลเวลา $t \in [0, 1]$ จากสูตร $(\text{speed} \times dt)$ โดยไม่ผูกกับอัตราเฟรมเรต ความเสียหายเกิดขึ้นเมื่อตัวจำลองกระสุนชนกับ Collider ณ จุดปะทะ ไม่ใช่การทำความเสียหายทันทีทั้งเส้นแบบ Hitscan
2.  **โหมด Melee Collider ติดตัวยูนิต (Melee Mode)**:
    ใช้สำหรับหมัดและอาวุธระยะประชิด Collider ของอาวุธจะเปิด/ปิดตามจังหวะแอนิเมชัน และเคลื่อนที่ตามตัวยูนิต โดยส่งความเสียหายเพียง 1 ครั้งต่อการชน และจะไม่โดนซ้ำจนกว่าเป้าหมายจะออกจากระยะและเข้าชนใหม่

### สูตรคำนวณความเสียหายและตารางตัวคูณเกราะ (Damage Matrix)
ความเสียหายที่เกิดขึ้นคำนวณจากความสัมพันธ์ระหว่างชนิดการโจมตี (`damageType`) และชนิดเกราะป้องกัน (`armorType`) ผ่านตารางตัวคูณ 2 มิติ โดยสูตรคำนวณความเสียหายพื้นฐานเป็นดังนี้

$$\text{damage} = \text{baseDamage} \times \text{Table}[\text{damageType}][\text{armorType}]$$

ชนิดของความเสียหายและเกราะแบ่งออกเป็น 4 ประเภทมาตรฐาน ได้แก่ Default (เนื้อ/หมัด), Bullet (กระสุนดินปืน), Explosion (แรงระเบิด), และ Lazer (ลำแสงพลังงาน)

รายละเอียดตารางตัวคูณความเสียหาย (Damage Multiplier Matrix):

| ชนิดการโจมตี \ ชนิดเกราะ | Default | Bullet | Explosion | Lazer |
| :--- | :--- | :--- | :--- | :--- |
| **Default** | 1.00 | 1.25 | 0.90 | 0.75 |
| **Bullet** | 1.25 | 0.75 | 0.85 | 0.50 |
| **Explosion** | 1.40 | 0.90 | 0.70 | 0.80 |
| **Lazer** | 1.60 | 1.40 | 1.10 | 0.60 |

*หมายเหตุ*: ตัวเลขในตารางแสดงค่าน้ำหนักสัมพัทธ์ โดยค่าที่มากกว่า 1.00 คือการโจมตีชนะทางเกราะ และค่าน้อยกว่า 1.00 คือเกราะสามารถลดทอนความเสียหายได้ชนิดเดียวกันต้านทานกันเอง

## 5. สถาปัตยกรรมปัญญาประดิษฐ์และสถานะการทำงาน (AI Architecture & FSM Engine)

ระบบปัญญาประดิษฐ์ของยูนิตศัตรูใช้สถาปัตยกรรมเครื่องสถานะจำกัดแบบสองชั้น (Dual-Layer State Machine Engine) เพื่อลดภาระการคำนวณกราฟค้นหาเส้นทาง (Pathfinding) บนเว็บบราวเซอร์

```
[ General Planner (Level/Path Layer) ]
  ├── วางโซ่ Pivot Points (A -> B -> C)
  ├── จองเลนการเดิน (Left / Center / Right Lane)
  └── คุมขอบเขตด้วย Pi Sector Cones
         │
         ▼
[ Unit Stage Machine (Individual AI Layer) ]
  ├── Stage 1: ค้นหา / เดินตามโซ่ General
  ├── Stage 2: ตรวจจับศัตรู (Pi Ring + Raycast Fan) -> Stage โจมตี
  └── Stage 3: HP ต่ำ (~30%) -> Stage ถอย / หา Medic / รักษาระยะ
         │
         ▼ (หากติดขัดหรือหลุดเส้นทาง)
[ Local General Fallback (Group Repair Engine) ]
```

### 1. ชั้นวางแผนระดับสูง (General Planner Layer)
General ทำหน้าที่ประมวลผลการเดินของกลุ่มยูนิตในภาพรวมระดับ Path ($1024$) และ L1 ($512$) โดยไม่คำนวณพิกัดระดับพิกเซลของยูนิตทุกตัวในทุกเฟรม

*   **การสร้างโซ่จุดอ้างอิง (Pivot Chain)**: General จะวางจุดอ้างอิงลำดับ $A \rightarrow B \rightarrow C$ เชื่อมระหว่าง Path เพื่อให้กลุ่มยูนิตเคลื่อนที่ไปตามโซ่
*   **การจองเลนเดิน (Lane Reservation)**: กระจายกลุ่มยูนิตออกเป็นเลนซ้าย กลาง และขวา ตามทิศทางการกำเนิดเพื่อป้องกันไม่ให้ยูนิตทุกกลุ่มเดินทับเส้นทางเดียวกัน
*   **ขอบเขตทิศทางแบบ Pi Sector**: ควบคุมพื้นที่การเดินของยูนิตด้วยรูปกรวย Pi องศา (มุมประมาณ 45 องศา) โดยมีจุดศูนย์กลางอยู่ที่จุดเริ่มต้นของช่วง $(A)$ ขยายรัศมีไปหาปลายช่วง $(B)$
*   **กลไกกันเส้นทางสั่น (Boundary Hysteresis)**: เมื่อผู้เล่นเคลื่อนที่อยู่บริเวณขอบระหว่าง Path ตัว General จะยังไม่เปลี่ยน Path เป้าหมายจนกว่าเป้าหมายจะเคลื่อนเข้าสู่ L-cell ฝั่งใหม่เต็มทั้งช่อง

### 2. ชั้นสถานะยูนิต (Unit Stage Machine Layer)
ยูนิตแต่ละตัวจะรับคำสั่งช่วงการเดิน $A \rightarrow B$ จาก General และประมวลผลสถานะภายใน 3 Stage หลัก:

*   **Stage 1: ค้นหาและเคลื่อนที่ (Search & Travel)**: เดินตามช่วง Pivot ที่ได้รับ เมื่อเดินเข้าสู่ Trigger ของจุด $B$ จะได้รับช่วงถัดไป $B \rightarrow C$ ทำงานเป็นลูปจนกว่าจะถึงปลายโซ่
*   **Stage 2: ตรวจจับและโจมตี (Engage & Combat)**: ตรวจจับเป้าหมายด้วยพัด Raycast ด้านหน้า ($1 \rightarrow 3 \rightarrow 5$ เส้น ในมุมประมาณ 45 องศา) ร่วมกับรัศมีวงกลม Pi รอบตัวระยะประชิด เมื่อพบศัตรูจะเปลี่ยนสถานะเป็นโจมตี หากยูนิตเคลื่อนที่หลุดออกนอก Pi Sector ของ General ยูนิตจะปรับสถานะกลับเข้าสู่เส้นทางหลัก
*   **Stage 3: การถอยและเอาชีวิตรอด (Retreat & Survival)**: เมื่อ HP ลดลงต่ำกว่าเกณฑ์ประมาณ 30% ยูนิตจะเข้าสู่ Stage ถอย โดยเคลื่อนที่ไปซ่อนด้านหลังยูนิตที่มีเกราะ/อาวุธแข็งแกร่งที่สุด หรือเคลื่อนที่ไปหายูนิตสายช่วยเหลือ (Medic)

### 3. ระบบประมวลผลสำรองกลุ่มย่อย (Local General Fallback)
หากยูนิตหรือกลุ่มยูนิตเกิดการติดขัดสิ่งกีดขวางจนงบการหักเลี้ยวหมดลง (Steering Budget) ยูนิตดังกล่าวจะแยกตัวออกมารันระบบ Local General เฉพาะกลุ่มเพื่อคำนวณทางหลบสิ่งกีดขวางเฉพาะหน้า และเมื่อเดินทางกลับเข้าสู่จุดหมายโซ่หลักได้แล้ว จะยกเลิก Local General และกลับเข้าสู่การควบคุมของ General หลักตามเดิม

## 6. สถาปัตยกรรมทรัพยากรและการกำเนิดแมพ (World Generation & Resource System)

ระบบกำเนิดทรัพยากรธรรมชาติทำหน้าที่กระจายวัตถุลงบนกริด $L3$ ($64 \times 64$) ภายในแต่ละ Path ตามสภาวะโหมดที่ Host กำหนด

*   **โหมดแมพแบบ Flat World**: โลกว่างเปล่า ไม่มีวัตถุทรัพยากรธรรมชาติ เหมาะสำหรับโหมดทดสอบและการเล่นแบบเน้นย้ำความเร็ว
*   **โหมดแมพแบบ World Type**: สุ่มกำเนิดทรัพยากรตามโควตาเปอร์เซ็นต์ต่อ 1 Path ได้แก่ ต้นไม้ (Tree), หิน (Rock), แร่เหล็กธรรมดา (Iron Ore), และแร่เหล็กขั้นสูง (High Iron Ore)
*   **กลไกการทำลายและการทำเหมือง (Harvesting Matrix)**: วัตถุธรรมชาติใช้โครงสร้างตารางสูตรเดียวกับอาวุธ โดยความเสียหายคิดจาก $\text{damage} = \text{base} \times \text{Table}[\text{toolTier}][\text{objectType}]$ หากใช้เครื่องมือไม่ตรงประเภท ค่าตัวคูณในตารางจะเป็น 0 ทำให้ไม่สามารถทำลายวัตถุนั้นได้

## 7. สถาวะการทำงานของแอปพลิเคชันและการแสดงผล (App Flow, State Machine & Render Engine)

แอปพลิเคชันทำงานแบบสถาวะเครื่องคงที่ (Deterministic State Machine) โดยแบ่งขั้นตอนการทำงานออกเป็น 5 สเตทหลักดังนี้

```
[ BOOT ] ──► [ MENU ] ──► [ LOADING ] ──► [ PLAYING ] ──► [ RESULT ]
  │                                                           │
  └──────────────────────── (กดปุ่มกลับเมนู) ──────────────────┘
```

รายละเอียดการทำงานของแต่ละสถานะแอปพลิเคชัน (App State Flow):

1.  **BOOT State**: ตรวจสอบ DOM โหลดโมดูล ES ขนาน ป้องกันการค้างด้วย Watchdog timer และเตรียมความพร้อมไฟล์ Asset
2.  **MENU State**: แสดงหน้าจอหลัก เลือกโหมดการเล่น (ในเวอร์ชัน V1 รองรับโหมด Local Host เล่นคนเดียวบนเครื่อง)
3.  **LOADING State**: ทำการสร้าง Object Pools ขนานไปกับการเจนโลก (World Gen) และคำนวณการจองช่องว่าง (Place Slots) เพื่อป้องกันปัญหาขยะความจำ (Garbage Collection สะดุด) ระหว่างเล่นแมทช์
4.  **PLAYING State**: รันรอบลูปเกมหลัก (Game Loop) แสดงผล UI HUD (เวลา Wave, ค่า HP, แถบ Hotbar active) ประมวลผลตรรกะการแพ้/ชนะ
5.  **RESULT State**: แสดงแผงสรุปผลแพ้/ชนะ (แพ้เมื่อ Base Block 3x3 พังทลาย, ชนะเมื่อเคลียร์ Wave ตามเป้าหมาย) ทับบนจอภาพ และมีปุ่มกดเพื่อกลับสู่ MENU State

### การบันทึกและคืนค่าสภาวะ (Snapshot Autosave & Persistence)
ระบบรองรับการบันทึกสภาวะการเล่นอัตโนมัติ (Autosave Memento) ทุกๆ 45 วินาทีลงใน `localStorage` เมื่ออยู่ในสเตท PLAYING พร้อมรองรับการดาวน์โหลดไฟล์บันทึกสภาวะเป็นรูปแบบไฟล์ `.json` เพื่อนำกลับมาโหลดคืนค่า (Restore/Import) ผ่านหน้าเมนูหลักได้

### สถาปัตยกรรมแสดงผลและการควบคุมหน่วยความจำ (Render Engine & Memory Control)
*   **Unit Pooling**: จำกัดการสร้างวัตถุยูนิตพร้อมกันไม่เกิน 100 ตัวในระบบ เมื่อยูนิตตายจะทำการซ่อนตัวและนำกลับมารีเซ็ตสเตทเพื่อใช้ใหม่ ป้องกันการจองหน่วยความจำใหม่
*   **Canvas Path2D Caching**: ทำการประมวลผลเบเกอร์ (Bake) อาร์ตแบบ Vector SVG หรือ Bitmap ความละเอียดต่ำเป็นออบเจกต์ Path2D ในแคชความจำตอนเข้าสเตท BOOT และ LOADING เพื่อลดภาระการวาดบน Canvas แบบเรียลไทม์
